# 翻译覆盖与可维护性

本指南用于修复漏译、误译和动态页面回归。两个插件的运行包保持独立；根层统一验证入口和回归要求，站点自己的路由、保护规则与词条保留在插件内。

## 先确定漏译发生在哪一层

只记录固定界面英文、标准化页面类别、控件类型和最小脱敏 DOM。不要把真实文件名、用户名、设计内容、正文、输入值或完整私人 URL 放进测试、日志或报告。

| 现象 | 优先核对 | 修改位置 | 必须覆盖的回归 |
| --- | --- | --- | --- |
| 固定词条在安全控件内也无法匹配 | 人工覆盖和生成词库是否已有条目、路由词库优先级、空白或标点差异 | `src/official-overrides.js` 或 `src/core.js` | 原英文命中目标中文；相同英文作为名称或正文时保持不变 |
| 词库已有词条，但真实控件不翻译 | 保护规则是否误把整个工具栏、侧栏或弹窗排除 | `src/content.js` 的 DOM 保护与上下文判断；纯文本判断在 `src/core.js` | 同一容器中固定控件翻译，名称、设计文字或正文仍受保护 |
| 一个词条被图标或多个子元素拆开 | 文本节点结构、空白节点、快捷键、无障碍标签是否参与匹配 | `src/content.js` 的节点处理 | 文本/属性对应翻译，子元素、事件与快捷键不丢失；关闭恢复原结构 |
| 首次加载正常，菜单打开或导航后漏译 | MutationObserver、扫描队列、路由变化与节点复用 | `src/content.js`；路由分类在 `src/core.js` | 初次扫描、异步插入、同节点改文案、无刷新导航及重复扫描 |
| 关闭后出现旧英文或中文残留 | 节点原文缓存与站点自身更新的关系 | `src/content.js` 的写入和恢复路径 | 翻译后站点改值；关闭应恢复最新站点原文；再次开启结果一致 |
| 报告缺项、泄漏名称或路由无效 | 安全候选规则、内容脚本发送值、后台接收验证 | `src/core.js`、`src/content.js`、`src/background.js` | 安全未知词条可记录；名称/输入/正文不记录；后台拒收不合规消息 |

先用最小测试复现，再修对应层。已被词库覆盖的词条漏译，不要通过重复添加同义词掩盖上下文或生命周期错误。修改保护范围时收窄到能确认的固定控件，并保留其周围用户内容的反例。不得靠清除整个保护容器、替换整段 `innerHTML` 或扩大正则为任意字符串来提高表面覆盖率。

## 回归用例应包含一对正反场景

每次翻译核心、DOM 保护、审计或恢复行为变化，至少覆盖：

1. **正向翻译**：固定控件中的已知词条翻译正确，空白和非文本子元素不丢失。
2. **保护对照**：相同英文作为文件/图层/仓库名、正文或输入值时完全不变。不能只用词库中不存在的字符串测试保护。
3. **动态变化**：异步插入、复用节点更新文本或属性、SPA/Turbo 导航后仍符合前两条。
4. **关闭与重启**：文本和属性恢复站点最新原文；重新开启不会重复翻译、恢复旧值或污染审计。

纯词条补充可以只增加对应核心命中用例；一旦调整容器、选择器或文本拼接，就需要 DOM 对照与恢复用例。选择器测试使用能表达语义的最小结构，并给保护反例使用相似结构，避免让测试仅复刻实现中的选择器字符串。

| 文件 | 稳定职责 | 不应混入的职责 |
| --- | --- | --- |
| `src/official-overrides.js` | 已核对的固定术语和人工覆盖 | DOM 遍历、网络翻译、用户内容替换 |
| `src/core.js` | 可直接测试的匹配、路由、文本判断与审计候选过滤 | DOM 保护选择器、定时器、全页观察、设置持久化 |
| `src/content.js` | DOM 保护与观察、按上下文翻译、可逆恢复、发送候选 | 无上下文扩大词库、持久化完整页面内容 |
| `src/background.js` | 开关、存储边界、验证收到的审计数据 | 默认信任内容脚本传入的任意字符串 |
| `generated/` | 固定来源生成的离线词库和元数据 | 手工补词、为日常测试刷新来源 |
| 根 `scripts/`、`tests/` | 编排双方检查、验证共同工程契约 | 让某个扩展运行时依赖另一个插件或根目录 |

两个独立 `verify-project.mjs` 的共同门禁通过根 `tests/verification.test.mjs` 的同一组场景约束；新增共同政策必须对两者执行。不要为消除小段重复而建立影响独立安装或打包的运行时依赖。只有双方行为语义相同、保护边界相同、打包后仍独立且已有回归覆盖时，才考虑提取共享实现。

## 日常检查与发布检查

根目录首次准备环境：

```powershell
npm ci
npm ci --prefix figma-zh-ui
npm ci --prefix github-zh-ui
npm run check
```

单插件可以独立运行 `npm test` 和 `npm run verify:offline`。根 `npm run test:tooling` 单独验证共同门禁，`npm run check:memory` 单独检查工程记忆。

根开发依赖只用于浏览器测试，不进入任何扩展运行包。涉及 manifest 加载、后台、消息、设置同步、弹窗或本地报告导出时，再运行：

```powershell
npx playwright install --no-shell chromium
npm run test:browser
```

`tests/browser/extensions.spec.mjs` 用同一组流程测试两个插件的原始 MV3 清单、独立脚本环境、保护边界、非目标域不注入、动态导航、真实 storage/onChanged/runtime 消息、弹窗启停及导出/清空。所有网页响应由测试提供，扩展 API 不使用替身，弹窗以扩展页面方式打开；真实站点 DOM 和工具栏弹窗用户手势仍属于人工验收。CI 将这层作为单独 Linux 任务，保留 Windows/Linux 的快速 `check`。浏览器下载只发生在开发环境，扩展运行时仍保持离线。

`verify:offline` 只跳过 24 小时来源年龄要求；无效/未来日期、无效 SHA、权限扩张、内容脚本范围/顺序变化、版本不一致、缺文件和静态检查错误仍会失败。它不会自动刷新上游，也不提供发布证明。`verify` 和现有打包脚本继续保留 24 小时来源要求。

静态网络扫描用于捕获常见调用和显式远程脚本导入；动态别名、间接加载和页面自身网络活动仍需代码审查与浏览器检查。浏览器扩展权限或运行时依赖有意变化时，应先按根 AGENTS 获得必要确认，再同步文档、清单、门禁和测试，不能先放松检查。

发布仅在对应插件目录执行 `update:sources` → `test` → `verify` → `package`；审查生成词库、来源 SHA、许可证和第三方声明的差异。两个插件分别发布，不因一方修复而更新另一方词库。

## 真实页面验收与交付记录

本机安装 Chrome 或 Edge 后，可从根目录运行可选的浏览器合成冒烟，参数为浏览器可执行文件的绝对路径：

```powershell
node scripts/browser-smoke.mjs "C:\Program Files\Google\Chrome\Application\chrome.exe"
node scripts/browser-smoke.mjs "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
```

按本机实际安装路径选择其中一条。脚本通过本地合成页面加载当前词库和运行代码，使用 Chrome API 替身验证翻译、保护、动态更新、恢复和审计关闭；不依赖浏览器登录会话，不加载已安装的扩展，也不进入默认 `check` 或 CI。它可以发现浏览器与 jsdom 的行为差异，但不能证明扩展权限、实际站点 DOM 或账号可见页面已经验收。

DOM 测试无法证明当前站点全部 DOM 已覆盖。涉及选择器、导航、保护或恢复时，按 [Figma 验收矩阵](../figma-zh-ui/README.md#验收建议) 和 [GitHub 验收矩阵](../github-zh-ui/README.md#覆盖保证) 在 Chrome/Edge 检查；没有实际浏览器或账号可访问某页时，明确记为“未验收”，不要将合成 DOM 测试写成真实页面通过。

交付记录应区分：已复现并修复的场景、自动回归结果、真实页面已验收范围、来源过期导致的发布限制，以及仍待页面证据的漏译。正常受保护的用户内容不计作待翻译 UI；词库条目数也不等于页面覆盖率。完成仓库修改后仍按根 AGENTS 执行记忆同步、提交与推送。
